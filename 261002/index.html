Before you start

Prerequisites

Check both before the workshop. The hands-on builds in Sections 4 and 5 depend on them.

  1. A Microsoft Copilot Premium license Check it in the bottom-left corner of the Copilot UI, where your profile and licence are shown. If it does not show a Premium licence, ask your IT admin before the session.
  2. Access to Frontier Your organisation's IT admin enrols users in the Microsoft 365 admin center → Copilot → Settings → Copilot Frontier. After enrolment, features can take about 3 hours to appear. Frontier agents show in the Agent Store labelled "(Frontier)".
For Sections 4 and 5

Section 4 — RFP Checker is built in Microsoft 365 Copilot (Premium) Agent Builder with custom skills, which need Frontier. Section 5 — Use Case 17 can be built either in Agent Builder or in Copilot Studio on the GitHub Copilot harness. Each harness's requirements and capabilities apply. If you build in Copilot Studio, make sure you can open a Copilot Studio environment your organisation has set up for the workshop.

Section 1

Microsoft 365 Copilot — what it is before you build on it

The equation

M365 Copilot = LLM + Work IQ + In-app Copilot experience + Web IQ

Every agent in this workbook is built on this product, not beside it. Before choosing a harness (Section 2) you need to know what the platform already gives you for free — because capability you can get from the product is capability you should not design into an agent.

Reading the equation, one term at a time

The LLM is the reasoning half, hosted in the Microsoft Cloud. On Copilot Chat (Basic) this is GPT; on Microsoft 365 Copilot (Premium) you additionally get model choice across GPT and Claude. Two properties hold on both tiers: the models are not trained on your organisational data, and Copilot inherits the security, compliance and privacy policies already set in Microsoft 365 — it does not introduce a second permission model.

Work IQ is, in Microsoft's own words, "a workplace intelligence layer that enables agents to access and reason over organizational data, context, and tools." It continuously builds a semantic understanding across Microsoft 365 and external systems, with permission-aware governance built in. It does not replace Microsoft Graph — the two work together, with Graph remaining the grounding path into tenant content. Learn describes Work IQ as combining chat, context, tools and workspaces:

Work IQ Four capabilities, one intelligence layer

01 ChatConversational intelligenceSupports A2A for agent-to-agent collaboration and REST for web applications, so agents can delegate work, maintain continuity and return fully processed, Copilot-quality responses.
02 ContextNo orchestration overheadWork IQ assembles and grounds context internally across organisational data to provide agent-ready inputs, so agents do not stitch together raw signals or manage retrieval pipelines.
03 ToolsFast, composable actionsThe Work IQ MCP collapses hundreds of operations into 10 generic tools reaching mail, calendar, files, people, chat and sites — simple verbs such as fetch, create and update.
04 WorkspacesLong-running agent workflowsSharePoint Embedded working storage gives agents a persistent space inside your tenant boundary for intermediate data and outputs — supporting task progression, reuse of results and handoff between agents.

Two of these matter more than they first appear. Context is why the same prompt behaves differently in Copilot than in a generic assistant — the grounding is assembled for you rather than stitched together from raw signals. And Workspaces is the one most people miss: persistent storage inside the tenant boundary is exactly what a stateless sandbox cannot offer, which is why it resurfaces as a design constraint in Sections 4 and 5.

Developers can reach Work IQ directly from custom apps and agents through the Work IQ API — A2A, a remote MCP server and a REST API. Note the commercial detail: "Work IQ API access is independent of Microsoft 365 Copilot licensing and available through usage-based billing." For licensed users it is present across all Copilot experiences and agents, but custom and third-party agents are billed on usage.

The in-app Copilot experience is where the intelligence is spent. On Basic, Copilot reaches into Outlook — and Copilot Chat in Outlook now reasons over the whole inbox, calendar and meetings rather than a single thread. On Premium it spans Outlook, Teams, Word, Excel and PowerPoint, adds Edit with Copilot, and brings AI-powered Search, Notebooks and Create. This is the "in the flow of work" half: the same reasoning, surfaced where the artefact already lives instead of in a separate chat window.

Web IQ supplies real-time public web grounding. It is the term for the web-search half of the answer, and it is available on both tiers — Copilot Chat's baseline offer is secure, web-grounded chat. The practical consequence for design: web grounding is never the differentiator between tiers; Work IQ is.

Section 1.3

How Microsoft 365 Copilot works — and where code interpreter fits

A prompt does not go straight to a model. Understanding the path it does take is what lets you predict which of your agent's requirements the platform will satisfy and which it will quietly drop.

Grounding and tool calls run sequentially on this harness — not in a loop.

The path a prompt takes

  1. You prompt — from Copilot Chat, from inside Word, Outlook, Teams, Excel or PowerPoint, or from an agent built on the chat harness.
  2. The orchestrator pre-processes it — it interprets intent and decides what grounding and which capabilities the answer needs. This is the component you do not control on the Copilot chat harness (Section 2.3).
  3. Grounding is retrieved — Work IQ for tenant content (always within your existing permissions, never more), Web IQ for public content, plus any knowledge sources or actions the agent declares.
  4. The grounded prompt goes to the model — hosted in the Microsoft Cloud; your data is not used for training.
  5. The response is post-processed — responsible-AI checks, compliance and security review, citation assembly — then returned with the actions the user can take on it.

Two design consequences fall straight out of this. First, permissions are enforced at grounding time, so an agent can never widen what a user can see — but it can surface content the user had forgotten they had access to, which is a governance conversation worth having early. Second, on the chat harness, grounding and tool calls run sequentially rather than in a loop — so "retrieve, then decide, then retrieve again based on what you found" is not a shape this harness supports.

What code interpreter is

Code interpreter is a capability, not a model. It lets Copilot — and any declarative agent that declares it — write and run Python in a sandboxed environment managed by Microsoft, then return both the result and the code it generated. The runtime is ephemeral: it spins up for the computation and tears down afterwards. No Azure subscription, no external service, no API keys.

It exists because language models are unreliable at arithmetic and cannot produce a real file. Code interpreter closes both gaps at once: it computes deterministically, and it emits downloadable artefacts.

When does it trigger?

This is the part most builders get wrong. You do not route to code interpreter — the orchestrator decides. Declaring the capability tells the orchestrator "this agent is allowed to run code"; it then invokes the sandbox when it judges that a request needs computation, a generated file, or a visualisation it cannot produce in prose. There is no branch to author, no condition to write, and no guarantee it fires on any particular turn.

Because it is probabilistic, the reliable lever is instructions. A line such as "When performing calculations involving rates, accruals or financial projections, use the code interpreter to ensure accuracy" materially increases the hit rate. That is a design pattern worth adopting whenever numbers appear in an answer users will act on.

What is preinstalled

Microsoft does not publish a package manifest for the code interpreter environment. There is no documented list of Python libraries and no supported way to query one, and because the sandbox has no outbound network, you cannot install anything at runtime either. The environment is fixed, opaque and not extensible.

What the documentation gives you instead is evidence of capability, which is the more useful thing to design against. The published examples confirm the environment can, without any setup on your part:

  • Write Word, Excel, PowerPoint and PDF files, and read those same formats plus CSV/TSV and TXT/UTF8 as input.
  • Render charts and graphs — line graphs, bar charts — from computed or uploaded data.
  • Produce QR codes and word clouds.
  • Perform image manipulation on uploads — greyscale conversion, banners, captions.
  • Solve symbolic and numerical maths, including definite integrals.

Treat that as the contract. If your scenario needs something outside it — a niche statistical package, a proprietary SDK, an external API call mid-computation — this harness cannot host it, and you are looking at a harness decision rather than a configuration one.

Design consequences of the lifetime rule

Because the VM is created per run and destroyed with the session, three things follow that catch teams out. There is no state between runs — a variable, dataframe or intermediate file from an earlier computation is gone, so any multi-step analysis must be re-derived from inputs each time. There is no artefact archive — if the user does not download the file during the session, it is not recoverable, so an agent whose value depends on a durable deliverable needs somewhere real to write it. And long-running work has no home here — the quotas bound execution time deliberately. Cowork's persistence model (Section 1.4) exists precisely because these three limits are real.

Understanding Cowork

Cowork is in this workbook as a worked example of an agent, not as a product tour. It is the clearest Microsoft-built illustration of the design decisions Sections 4 and 5 ask you to make yourself: a fixed set of skills that load only when a task needs them, an execution context that keeps nothing between sessions, output written somewhere durable, and an approval gate in front of every consequential action.

Read its shape as a reference design. The ephemeral-versus-persistent boundary above is the same boundary your own agent has to draw, and Cowork draws it where the compute is disposable and the output is enterprise content. When you design your own agent in Sections 4 and 5 and find that a stateless sandbox will not hold your intermediate files, this is the model you are comparing against.

Known limits

Cowork cannot reach files stored locally on a device — it works in OneDrive and SharePoint. It cannot delete files or folders in either. It cannot read encrypted files even when you have access, and attached files must be under 200 MB. Microsoft does not validate user-authored custom skills, so their output needs the same review you would give a colleague's first draft.

Section 2

Agents and Harness — what is a harness?

The equation

Agent = LLM + Harness

An LLM on its own is not an agent. It generates text and stops. What turns it into something that performs work is the harness — and Microsoft Agent Framework says exactly that: an agent harness is "the runtime scaffolding that turns a language model into an agent that can perform work."

Reading the equation, one term at a time

The LLM is the reasoning and generation half. It interprets intent, plans in language, and writes the output. It has no memory of your last session, no ability to call a system, and no way to act on what it produces.

The harness is everything around it — "a runtime that exists between the two: it determines when to call the model, what components to send it, interprets what comes back, and calls the right tools." Concretely it:

  • Drives model and tool calls — chooses when to invoke the model, and which tool to call with which arguments.
  • Manages conversation state and context — sessions, history persistence, and context compaction when the window fills.
  • Applies approval policies — standing approvals, auto-approval rules, and human-in-the-loop gates on tool execution.
  • Keeps the agent progressing through a multi-step task — planning, todo tracking, and optional bounded re-invocation driven by evaluators or predicates.

Note what this means: neither term of the equation is something you write. You select a model and you select a harness. So where does the building happen?

Your design is the third thing — and it is built around the chosen harness

What you actually author is the design layer, and it has three components:

The design layer The three things you actually author

IInstructionsDefine the agent's role, scope, tone and boundaries — and direct it on which resources to call, how to fill tool inputs, and how to respond.
KKnowledgeThe grounding sources the agent answers from — SharePoint, files, Dataverse, connectors, approved websites — so answers are anchored in your content rather than invented.
TToolsWhat the agent can do beyond talking — connectors, APIs, MCP servers, flows and other agents it can invoke.

All three sit on top of the harness you choose — never independently of it

This triad is Microsoft's own packaging, not a teaching device. Copilot Studio puts it plainly: "All harnesses let you combine generative AI, knowledge, and actions to create modern agents built for how your teams actually work." And the triad belongs to the agent rather than to whatever calls it — when a workflow hands a step to an agent, "the agent's own instructions, knowledge, and tools are already configured wherever the agent was built."

The consequence that drives this whole workbook

The design layer is built around the chosen harness — never independently of it. The harness decides which of the three components you can express, how richly, and whether some are available at all. An 8,000-character instruction ceiling, whether tools can be orchestrated across steps or only called once, whether knowledge can be reasoned over or merely retrieved: all harness properties, inherited the moment you choose where to build.

Why the harness matters to you as a builder

The Copilot Studio guidance names four consequences, and each one is a design constraint you inherit the moment you pick a build surface:

Common mistake

Blaming the model for behaviour the harness owns. "The agent forgot what we discussed" is a state-and-context problem. "It stopped after one step" is an orchestration-loop problem. "It couldn't produce the Excel file" is a harness capability problem. Swapping the model fixes none of these.

Copilot chat harness — extend what people already use

The Copilot chat harness lets you extend Microsoft 365 Copilot Chat: connect enterprise knowledge so employees get grounded answers without leaving their everyday experience. It runs on current chat models and is built for connecting people to information — an onboarding agent answering from SharePoint is the canonical case. Publishing is to internal teams. Billing is consumption-based, or included in the Microsoft 365 Copilot user subscription license.

This is the harness most of your users meet first, because it is the one behind Agent Builder inside Microsoft 365 Copilot — plus pro-code declarative agents and declarative agents authored in Copilot Studio. There is no environment to provision, no solution to manage, and no publishing pipeline.

Design consequence: instructions are the whole steering mechanism, so the 8,000-character ceiling is a real design budget — and the reason skills exist (Section 3).

Standard harness — predictable, rule-based, authored

The standard harness is the classic Copilot Studio most makers already know: you define topics, prompts and paths, and the experience responds consistently for well-understood requests. It draws on your existing prompt library and enterprise knowledge, and it powers agent flows. Best fit: an internal help desk that answers common questions and routes simple requests through a workflow. Publishing reaches internal teams or external customers.

Design consequence: a fourth component joins the three — topics. Behaviour you would write as an instruction elsewhere, you author as a path here, and the runtime follows it rather than interpreting it.

GitHub Copilot harness — reasoning, files, recovery

The GitHub Copilot harness is the most capable option, built for reasoning-heavy agents and workflows that complete complex business processes. It became generally available on 3 August 2026. Open copilotstudio.microsoft.com and this is the harness you are presented with first; the standard harness sits behind Other ways to build. That is placement, not a lock-in — Microsoft is explicit that the two run alongside each other and "you choose which harness to use when you create a new agent." Instead of following a fixed script it takes a goal, breaks it into steps, calls tools across connectors, knowledge, MCP and connected agents, and adjusts when a step fails. Design consequence: you write fewer mechanics and more intent. Instructions state the goal and the guardrails; the harness supplies the plan, the retries and the recovery you would otherwise have had to author yourself.

Memory and workspace — what the words actually mean

This is the distinction most often stated loosely, so it is worth being precise about both halves.

Memory is part of Copilot Studio feature. On the GitHub Copilot harness, Memory is a preview capability the maker switches on per agent: "Memory in Copilot Studio helps an agent remember details from its interactions and use that context for future interactions." Its scoping is the important part — each agent keeps a separate memory store for every user, a user's memories are private to that user and invisible to the maker, memories are deleted after 28 days without interaction, and memory is disabled in group chats and Teams channels. Turning the toggle off stops the agent using memories but does not delete them.

Agent Builder has no equivalent. There is no memory toggle, and the declarative agent manifest carries no memory property. Worth separating from a similar-sounding feature: Microsoft 365 Copilot has its own personalisation memory for Copilot Chat users, stored in the user's mailbox — that is a property of the Copilot experience, not something your declarative agent can configure or reach.

Skills — what they are and how they are built

A skill is a modular capability you add to an agent so it performs a specific task more reliably and repeatably. Not more knowledge, and not another tool: a packaged procedure, with the assets and scripts that procedure needs travelling alongside it.

The one-line distinction

An agent is the "who". A skill is the "how". Add an agent when there is a new responsibility. Add a skill when there is a specific task that responsibility must perform the same way every time.

The anatomy of a skill

A skill is a file directory. Exactly one file is mandatory.

my-skill/
├── SKILL.md                 # REQUIRED
│   ├── YAML front matter    #   name + description  → how the model decides to use it
│   └── instructions         #   the procedure, under 20,000 characters
├── <resource files>         # optional — templates, reference data, definitions
└── <scripts or folders>     # optional — .py .js .mjs .cjs .ts .mts .sh .bash
                             #            max directory depth 3
  • SKILL.md holds the instructions that direct the model to complete the task. Its front matter carries the name and description — these are what the orchestrator reads to decide when the skill applies, so they are load-bearing, not labels.
  • Resource files are the assets the task needs: branded templates, KPI definitions, reference tables, schemas.
  • Scripts replace model-generated code with code you control — the same transformation, the same chart, every run.

A worked example from the documentation: a finance team builds a quarterly business review skill that bundles the instructions for producing the review, scripts that transform data and generate charts, and assets such as financial models, KPI definitions and branded slide templates. The agent reaches for the skill when a user asks for that task.

4.1.2 · From document comparison to RFP checking

The RFP Checker is a document comparison agent specialised to one job. It keeps the architecture of a document comparison agent — a derived rule set, a deterministic core with a thin judgement layer, typed artefacts between skills, and a completeness receipt — and changes one thing: what counts as a unit of comparison.

Document comparison works clause by clause, because two versions of one document share a structure and the question is what moved inside it. An RFP and its responses share no structure at all — one is a question set, the others are answers, each written to its own outline. So the RFP Checker works component by component, where a component is a requirement the RFP imposes. That shift produces three questions in place of one:

  • Is the component there at all? For each requirement, did this respondent address it — anywhere in their document, in whatever words they chose?
  • Is it substantive? A component can be present and still empty. "Details available on request" occupies the space a commitment should have.
  • Where components are present across respondents, how do they differ? This is the comparison proper — but it runs between responses, not between a response and the RFP, and only on the components everyone supplied.

The first two questions are why this agent earns its place. A silence is invisible to a reader working through documents one at a time, and silences are exactly what an RFP review exists to catch.

Scope — content, not craft

The RFP Checker reads content. It does not assess design, formatting, structure or tone, and it does not reward a well-written cover letter. Its question is only ever: is the required information here, is it substantive, and how does it compare with what the others said? A respondent with an unattractive document and complete answers must score better on every measure this agent reports than a polished document with gaps. Write that into the instructions — persuasive writing is exactly what an evaluation agent should be immune to.

4.3.2 · Instruction

With every procedure packaged as a skill, the instruction block carries only what is true on every run — about 7,600 characters against the 8,000 ceiling. It does seven things:

  • Sets the role and the limit. Establish what each response contains, omits and deviates on — and do not recommend an award.
  • Fixes the scope to content. Never assess formatting, design, structure or writing quality, and never let presentation move a verdict.
  • Names the three skills with their call conditions. For each: when to call it, what it requires, what it produces, and when not to call it.
  • Pins the protocol. Derive → confirm → check → report, in that order, with confirmation marked as a conversation rather than a skill.
  • States the refusal rules. Never invent a threshold, weight or volume; never report a verdict without a Requirement ID and a quoted span; treat "not stated" as a valid finding.
  • Separates coverage from conformance. The verdict records whether the respondent answered. Whether the value passes is a separate test that needs a threshold — and where the RFP left one open, the answer still counts as answered.
  • Defines the verdict vocabulary and the boundary. Five verdicts with explicit meanings, the [additional note] rule, and an explicit refusal to rank or award.

Every one of these is a decision from 4.1 and 4.2 written down in a form the runtime enforces. The full text sits in the build step (4.4), ready to copy.

    # RFP Checker — agent instructions

You help a procurement manager evaluate supplier responses against an issued RFP.
You establish what each response contains, what it omits, and where it deviates
from what was asked. You do not recommend an award.

## Scope

Assess CONTENT ONLY. Never comment on formatting, document design, section
structure, length or writing quality, and never let presentation influence a
verdict. A plain document with complete answers is a better response than a
polished document with gaps, and your output must reflect that.

Your only questions are: is the required information present, is it substantive,
and how does it compare with what the other respondents said.

## Skills

You have three skills. Each owns one stage of the work and produces a named
artefact the next stage consumes. Call them in order; never run one without the
artefact its predecessor produces.

### `rfp-requirements` — derive the register

CALL WHEN the user attaches an RFP and asks to check, evaluate or compare
responses against it, or asks what an RFP requires. Always first.

PRODUCES `requirements.json` — every obligation with a Requirement ID, source
reference, check type and engine, plus any threshold the RFP left unresolved.

DO NOT CALL to re-read a register already confirmed in this conversation.

### `response-check` — check submissions against the register

CALL WHEN the register is confirmed and submissions are available, or the
user adds a further response to an evaluation under way.

REQUIRES a confirmed `requirements.json`. If none exists, run
`rfp-requirements` first — never check against a register the user has not
seen.

PRODUCES `coverage.json` — one verdict per requirement per respondent, the
additional notes, and the coverage receipt.

DO NOT CALL before the register is confirmed, or to re-grade one requirement
in isolation — re-run the full check so the receipt stays true.

### `report-render` — build the report

CALL WHEN checking is complete and the user asks for the report, summary,
comparison or file; or immediately after `response-check` finishes.

REQUIRES `requirements.json` and `coverage.json`.

PRODUCES one self-contained `.html` file: per-respondent extracts, additional
notes, then the comparison table with the receipt in the header. Every cell of
the comparison table carries the verdict **and a short answer** — the stated
value, or the condensed extract — so the table can be read on its own.

DO NOT CALL with an incomplete coverage set. If any requirement × respondent
cell is unfilled, fix that first — a report that looks complete but is not is
the worst output this agent can produce.

## Protocol

Always work in this order. Never skip ahead, even when the user asks for "just
the summary":

1. DERIVE — read the issued RFP (the baseline) and build the requirement
   register. Skill: `rfp-requirements`.
2. CONFIRM — show the register to the user. List every requirement whose
   threshold the RFP left unresolved. Wait for confirmation before checking.
   No skill; this is a conversation.
3. CHECK — evaluate every submission against the confirmed register.
   Skill: `response-check`.
4. REPORT — render the single HTML report. Skill: `report-render`.

Step 2 is not optional. The register is the contract for every verdict that
follows, so a mistake there repeats itself across every respondent.

If the user attaches responses without an RFP, ask which document is the
baseline. Never infer it from filename alone.

If the user asks for something these three skills do not cover — drafting a
clarification letter, scoring against the evaluation weights, recommending a
supplier — say what you can provide instead. Do not improvise a substitute for
a skill you do not have.

## Refusal rules

These are absolute.

- NEVER invent a threshold, weight, volume or date. Where the RFP says `[TBC]`,
  `[Insert ...]` or leaves an empty bracket, report the values each respondent
  stated and ask the user to supply the missing figure. Do not guess an
  industry-standard value. See "Coverage is not conformance" below for how to
  grade these.
- NEVER report a verdict without a Requirement ID and a quoted span from the
  response.
- NEVER score or rank a respondent that has not passed the elimination
  criteria.
- NEVER treat a persuasive claim as evidence. "Industry-leading", "recognised
  by our recent award" and "fastest in the evaluation" are marketing, not
  answers.
- "Not stated" is a valid and frequently correct finding. Prefer it to a
  charitable reading.

## Coverage is not conformance

These are two different questions and must never be collapsed into one verdict.

- COVERAGE — did the respondent supply the information the requirement asks
  for? This is what the verdict records, and it is what this agent exists to
  establish.
- CONFORMANCE — does the value they supplied pass the threshold? This is a
  separate test, and it needs a threshold to test against.

When a respondent answers fully but the RFP left the threshold unresolved, the
verdict is `answered` — they did what was asked of them. Set `gate` to
`cannot_adjudicate` and record why. Do not mark it `not evaluable`; that would
penalise a respondent for the RFP's own gap and hide a complete answer.

Reserve `not evaluable` for a DERIVED check that cannot be computed because an
RFP input is missing — there the respondent was asked nothing, so there is no
answer to grade.

## Verdicts

Use exactly these values:

- `answered` — the requirement is addressed with a specific, checkable commitment.
- `partial` — addressed, but missing a figure, a date, a name or a commitment
  the requirement asked for.
- `evasive` — words occupy the space but no commitment is made. "Available on
  request", "details to follow", "we are confident that we can" are evasive.
- `absent` — nothing in the document addresses this requirement.
- `deviation` — a specific answer that conflicts with what the RFP required.
  State both values: required X, offered Y.

Grade on substance, never on confidence of tone.

## Additional notes

Anything a respondent offers that the register does not ask for goes into
`[additional note]` for that respondent. Surface it — it is often commercially
material — but never let it fill a gap. A respondent cannot improve coverage by
answering questions nobody asked. Additional notes are reported beside the
register, never inside it, and are never scored.

## Evidence discipline

Every verdict cites the Requirement ID and the passage it came from. Quote the
response's own words rather than paraphrasing.

Record a `stated_value` wherever the answer carries one — a price, a number of
weeks, a percentage, a contract term, a named inspection outcome. The report
uses it as the short answer in the comparison table. Two rules govern that
short form: it never replaces the full extract, and it must never condense so
far that the meaning changes. Where a response answers a
requirement in a place the RFP did not anticipate — a cover letter, a bid
summary table — that still counts; record where you found it.

## Vocabulary

Use the organisation's terms: respondent (not vendor or bidder), elimination
criterion, deviation, clarification, register, requirement.

## Boundary

You do not award, rank by weighted score, or name a winner. Weighted scoring
requires the RFP's evaluation weights to be filled in, and choosing a supplier
is the organisation's judgement. If asked to recommend one, produce the
comparison and state that the decision sits with the procurement manager.

financial-calculator / scripts/calculator.py
#!/usr/bin/env python3
"""calculator.py - deterministic Islamic-finance simulations for the
financial-calculator skill.

Standard library only. Every rate, nisbah and tenor is an INPUT: the script
holds no product figures of its own. Take them from the current rate sheet.

Subcommands
  murabahah   instalment simulation for murabahah financing
  bagi-hasil  profit-sharing estimate for deposito / tabungan (mudharabah)

Output is JSON on stdout. Invalid or missing input exits with code 2 and a
message on stderr - the agent must ask the user, never guess a value.
"""
import argparse
import json
import sys
from decimal import Decimal, ROUND_HALF_UP, getcontext

getcontext().prec = 34
ONE_RUPIAH = Decimal("1")


def rp(x):
    """Round to whole rupiah, half up."""
    return x.quantize(ONE_RUPIAH, rounding=ROUND_HALF_UP)


def fail(msg):
    print("ERROR: " + msg, file=sys.stderr)
    sys.exit(2)


def dec(value, name):
    try:
        return Decimal(str(value))
    except Exception:
        fail(f"{name} must be a number, got {value!r}")


# ---------------------------------------------------------------- murabahah
def murabahah(a):
    price = dec(a.price, "price")
    if price <= 0:
        fail("price must be greater than 0")
    if a.down_payment is not None and a.down_payment_pct is not None:
        fail("give --down-payment OR --down-payment-pct, not both")
    if a.down_payment_pct is not None:
        pct = dec(a.down_payment_pct, "down-payment-pct")
        if not 0 <= pct < 100:
            fail("down-payment-pct must be 0 to <100")
        dp = rp(price * pct / 100)
    else:
        dp = rp(dec(a.down_payment or 0, "down-payment"))
    if not 0 <= dp < price:
        fail("down payment must be at least 0 and less than the price")
    rate = dec(a.margin_rate, "margin-rate")
    if rate < 0:
        fail("margin-rate cannot be negative")
    n = a.tenor
    if n <= 0:
        fail("tenor must be at least 1 month")

    principal = price - dp
    schedule = []

    if a.method == "flat":
        total_margin = rp(principal * rate / 100 * Decimal(n) / 12)
        total = principal + total_margin
        inst = rp(total / n)
        base_p, base_m = rp(principal / n), rp(total_margin / n)
        bal = total
        for k in range(1, n + 1):
            last = k == n
            pay = bal if last else inst
            pk = principal - base_p * (n - 1) if last else base_p
            mg = pay - pk
            bal -= pay
            schedule.append((k, pay, pk, mg, bal))
    else:  # annuity (effective)
        r = rate / 100 / 12
        if r == 0:
            inst = rp(principal / n)
        else:
            inst = rp(principal * r / (1 - (1 + r) ** (-n)))
        bal = principal
        for k in range(1, n + 1):
            mg = rp(bal * r)
            last = k == n
            pk = bal if last else inst - mg
            pay = pk + mg
            bal -= pk
            schedule.append((k, pay, pk, mg, bal))
        total_margin = sum(s[3] for s in schedule)
        total = principal + total_margin

    rows = [
        {"month": k, "instalment": int(p), "principal": int(pk),
         "margin": int(m), "outstanding": int(b)}
        for (k, p, pk, m, b) in schedule
    ]
    preview = rows if n <= 6 else rows[:3] + rows[-2:]
    paid = sum(r["instalment"] for r in rows)
    assert paid == int(total), "schedule does not reconcile"
    return {
        "calculation": "murabahah",
        "inputs": {"price": int(price), "down_payment": int(dp),
                   "margin_rate_pct_pa": str(rate), "tenor_months": n,
                   "method": a.method},
        "result": {
            "financed_amount": int(principal),
            "total_margin": int(total_margin),
            "total_payable": int(total),
            "monthly_instalment": int(schedule[0][1]),
            "final_instalment": int(schedule[-1][1]),
        },
        "schedule_preview": preview,
        "check": f"{n} instalments sum to {paid} = total_payable",
        "notes": [
            "Simulation only - not an offer. Final terms follow the signed akad.",
            "Rounded to whole rupiah; the final instalment absorbs rounding.",
        ],

def bagi_hasil(a):
    nominal = dec(a.nominal, "nominal")
    if nominal <= 0:
        fail("nominal must be greater than 0")
    if a.days <= 0:
        fail("days must be at least 1")
    basis = dec(a.day_basis, "day-basis")
    if basis <= 0:
        fail("day-basis must be greater than 0")

    if a.equivalent_rate is not None and (a.nisbah is not None or a.gross_rate is not None):
        fail("give --equivalent-rate OR --nisbah with --gross-rate, not both")
    if a.equivalent_rate is not None:
        eq = dec(a.equivalent_rate, "equivalent-rate")
        basis_txt = "equivalent rate supplied"
    elif a.nisbah is not None and a.gross_rate is not None:
        nis = dec(a.nisbah, "nisbah")
        if not 0 <= nis <= 100:
            fail("nisbah (customer share) must be 0 to 100")
        gross = dec(a.gross_rate, "gross-rate")
        eq = nis / 100 * gross
        basis_txt = f"equivalent rate = nisbah {nis}% x gross rate {gross}%"
    else:
        fail("need --equivalent-rate, or both --nisbah and --gross-rate "
             "(take them from the current rate sheet)")
    if eq < 0:
        fail("rate cannot be negative")

    gross_share = rp(nominal * eq / 100 * Decimal(a.days) / basis)
    tax = dec(a.tax_rate, "tax-rate")
    if not 0 <= tax <= 100:
        fail("tax-rate must be 0 to 100")
    tax_amt = rp(gross_share * tax / 100)
    net = gross_share - tax_amt
    return {
        "calculation": "bagi-hasil",
        "inputs": {"product": a.product, "nominal": int(nominal),
                   "days": a.days, "day_basis": int(basis),
                   "equivalent_rate_pct_pa": str(eq.normalize()),
                   "tax_rate_pct": str(tax)},
        "result": {
            "gross_profit_share": int(gross_share),
            "tax": int(tax_amt),
            "net_profit_share": int(net),
            "balance_at_end_of_period": int(nominal + net),
        },
        "basis": basis_txt,
        "notes": [
            "Estimate only - actual bagi hasil depends on realised results and is not guaranteed.",
            "Rounded to whole rupiah.",
        ],
    }

# answer-format

## Shape

**Jawaban singkat** - one or two sentences that answer the question.

**Rincian** - the conditions, steps, figures or promo terms. Use a table when
comparing more than two items. Rupiah as `Rp 1.250.000`; dates as
`28 September 2026`.

**Sumber** - each document used: title, number, effective date (tanggal
berlaku), link. For a calculation: "Dihitung dengan financial-calculator" and
the inputs used.

**Catatan** - only what applies:
- "Simulasi, bukan penawaran. Ketentuan final mengikuti akad." (calculations)
- "Bagi hasil bersifat estimasi dan tidak dijamin." (funding estimates)
- "Promo berakhir <date>." (promos ending soon)
- "Dokumen yang lebih baru mungkin belum diunggah - konfirmasi ke <owner>."
  (when the newest document found is old)

## Rules

- Never include customer personal data in an answer or a file name.
- Do not soften or restate a requirement - quote it.
- If the answer is "tidak ditemukan", say that plainly and name who to ask.
- Keep it short enough to read on a phone in Teams.

Section 5.3

Try It Yourself

The step-by-step below is designed for prototyping Asisten Pengetahuan Marketing in Microsoft 365 Copilot Agent Builder. Similar steps can be applied to build it in Copilot Studio on the GitHub Copilot harness.

Steps

  1. Confirm the prerequisites. A Microsoft Copilot Premium licence and access to Frontier — see Prerequisites. Custom skills are preview and Frontier-gated; a Copilot licence alone is not enough, so check enrolment before anything else.
  2. Create the agent. From the Copilot Chat main UI, go to Agents in the side bar, then Create agent. Once you are in, select Skip to go straight to the Agent Builder configuration UI rather than the describe flow. Name it Asisten Pengetahuan Marketing.
  3. Give it the description. Paste the description from the Name & description row in 5.2.2. This is what users see before they open the agent.
  4. Paste the instructions. Open Configure and replace the generated instruction text with the block from 5.2.3 (2,064 characters — within the 8,000-character ceiling).
  5. Add knowledge. Under Knowledge, select + Add knowledge and add the SharePoint policy & regulation, product terms, product feature & benefit and promo programme libraries and the current rate sheet from 5.1.5. Check that the effective-date, status and promo-period columns are populated — the latest-version and expired-promo rules depend on them.
  6. Upload the four skills. Configure → Skills → Add, one .zip per skill. Upload the complete archive — a bare SKILL.md is rejected on this surface; the maximum is 8 skills per agent.
    • policy-lookup.zip — SKILL.md
    • product-promo-finder.zip — SKILL.md
    • financial-calculator.zip — SKILL.md + scripts/calculator.py
    • answer-format.zip — SKILL.md
  7. Check the capability. Configure → Capabilities → "Create documents, charts, and code" is on by default — leave it on, so the agent can hand over the full instalment schedule as an Excel file.
  8. Test in the preview pane. Use the Try it toggle and run the prompts from 5.2.5, then check at minimum:
    • a murabahah simulation with the illustrative inputs in 5.4 — the figures must match 5.4 exactly;
    • the same question without a margin rate — the agent must ask for it, not assume one;
    • a rule with two versions in the library — it must cite the newer one;
    • an expired promo asked for by name — it must say the promo has ended;
    • a question the libraries cannot answer — it must say "tidak ditemukan" and name an owner.
  9. Create and share the agent. Select Create to publish it to yourself, then Share it with the marketing pilot group (verify the sharing options in your tenant). An agent has to be published before it can be used in a normal chat — until then it only runs in the builder's preview pane.
